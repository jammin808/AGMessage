# AGMessage on the show network

AGMessage implements **Show Bus 1.2** (`docs/SHOWBUS.md`; master copy in Stagewatch). It is a `messenger` node. It
hears PlayMap's `playmap` kind (a Show Bus 1.3 proposal, PlayMap `docs/SHOWBUS-NODE.md`).

| What | How |
|---|---|
| Hello | UDP 9928 every 2 s: `{"t":"messenger","v":1,"proto":1,"id":<stable 8 hex>,"ports":{"http":3023,"https":3023},"caps":["messages","action-prompts","documents","ai","context","receipts","proposals","displays","help"],"clock":<unix ms>,"tls":"sha256:<hex>","build":"0.5.0+17.abc1234"}`. `build` is the build it runs (`app/lib/version.js`). Not sent when bound to loopback. |
| Peers | Every hello kind on 9928 (`main`, `agent`, `patterns`, `playmap`, `messenger`): live < 6 s, stale < 12 s, then dropped; a peer's `build` is kept when it is SemVer's alphabet within 64 characters. Admin → Show network. The hello is unauthenticated, so the table is bounded: at most 256 peers and 8 ids per address — a hello with a new id beyond that is dropped (and counted), while ids already heard keep refreshing — and its change reaches the admin page at most twice a second, latest wins. |
| HTTPS (§10) | The same port serves HTTP and HTTPS (a connection whose first byte is a TLS handshake is TLS). One self-signed ECDSA P-256 certificate per install, made with node:crypto, kept in `%LOCALAPPDATA%\AGMessage\tls.json` with its private key sealed; valid 825 days (Apple's limit) and renewed 30 days before it ends. `GET /tls`, `GET /tls.cer`. **Require HTTPS** (admin). |
| Stagewatch links | One per hall that has its own (the hall's Set up: address, `node`-scope key, fingerprint — kept sealed in `settings.json` → `hallStagewatch`, never in the room's own settings), and the default one (Admin → Show network) for every other hall. Each: `GET ws://<sw>/ws?node=<id>&t=messenger&cid=<id>&page=/agmessage`, where `<id>` is this AGMessage's Show Bus id (its hello's 8 hex characters, the same on the default link and every hall's; the hall's code is never in the address): Stagewatch's Screens list each AGMessage once under that id, and a name given to it there sticks to that one AGMessage (Stagewatch 2.16 reads `cid` and `page` and ignores `node` and `t`; 2.18 tells a link that names its node whether its key was accepted) (or `wss://` when Stagewatch announces a certificate, the address is `https://`, a fingerprint is typed, or the certificate is pinned) with `Authorization: Bearer swk_…` — never in the URL; the certificate checked against the pin for that node and for the link's own address before anything is sent — once pinned, a missing or spoofed hello never turns TLS off; removing a Stagewatch's address (in a hall's Set up, Admin → Show network, or by closing the hall) forgets its pins, unless another link follows that address; ping every 2 s for the clock offset (CLOCKS APART > 2 s); stale after 6 s quiet, dropped at once and redialled after 12 s (backoff 0.5 → 5 s with jitter). **Connected means Stagewatch accepted the key**: 2.18's first message on the socket, `{"type":"auth","ok":true,"node":…,"words":…}` (`ok:false` refuses, in its `words`), or — 2.16 says nothing of the key on the socket and sends its public frames to any key — a 200 to one authenticated `GET /api/context` on the first frame (a 404 in Stagewatch's first second, a 429 after its `Retry-After`, a 5xx or no answer: still checking, asked again while that socket is open; 401 or 403 refuses); a 401 to any later request (a send, the context, the desk) refuses too. Each new socket earns its own verdict. Only then is a certificate used for the first time pinned, the context fetched and posted, the desk asked and anything sent. The states every reader shows (the `stage` payload's `key`, `stage:targets.key`, `hall:settings.stagewatch.key`, health `stageKey {state, words, via, node, at}`): "checking key" (amber; frames dimmed, nothing sent), "viewing" (no key: the public timer, nothing sent, nothing pinned), "key refused: <Stagewatch's words>" (red; at most 120 characters, a `swk_…` in them cut). A refusal lets the socket go, drops that Stagewatch's context and desk, refuses sends and proposals with words and withdraws 🖥, and asks again only after 61 s (Stagewatch locks an address for the rest of a minute after 5 wrong keys, so a wrong key never locks out this machine's other links); a new key or address asks at once. Each change of verdict is one `stagewatch.key` audit row, never the key. A hall's frames reach only that hall's room and screens; a hall moved to another Stagewatch (or back to the default) tells its room and its screens at once. Saving a hall's Set up unchanged changes and records nothing; a save refused for its address (not a Stagewatch address) applies nothing, its new name neither. |
| Send to stage | `POST /api/message/<text>/<urgency>/off/ack` with `X-Request-Id: ag…` to the hall's Stagewatch; the receipt `{"stage":"accepted"\|"applied","refs":{"messageId"}}`; the live frame's `messageId` / `messageAck` / `messageAckBy` then mark that message seen / acknowledged. Sends and acknowledgements are keyed by link and message id (each Stagewatch numbers its own), and followed only while the link is on the Stagewatch the send went to: a link pointed elsewhere or made again, or frames whose `seq` goes back (Stagewatch restarted, Show Bus §4), number afresh, and a send still waiting when it can no longer be followed reads `lost` on its record (never `sent`, waiting for an acknowledgement that cannot come; one seen or acknowledged keeps that). The send keeps its link, its Stagewatch's address tag and the `seq` of that Stagewatch's frames then, so an AGMessage restart keeps following it only while that Stagewatch is the one it went to: on the same link and address, and not restarted since — the link's first frame after the restart has a `seq` no lower than the send's (one lower: `lost`). A Stagewatch that restarted while AGMessage was down and whose `seq` has already climbed past the send's cannot be told apart by `seq` alone (that needs a boot id in Stagewatch's frames). A down link refuses at once (nothing queued). |
| Show desk (§11) | When a hall's Stagewatch keeps the approval queue (`approvals` in its hello's caps, or `GET /api/proposals?from=` answers), a message can be asked of the operator with a destination (`app/lib/stagelines.js`): the speaker's screen `message "<text>" <info\|warn\|crit> off ack`; a role screen `signal message <moderator\|backstage\|interpreter> "<text>"`; a department its context has named since it was linked `signal message "<Dept>" "<text>"` (Stagewatch lists a department by its newest cue — kind `department` for a standby or GO, `cue` once messaged — so departments appear once Stagewatch has cued them this session); the operator alone `note "<text>"`. Only a destination the hall's Stagewatch offers, only urgency `info`/`warn`/`crit` (anything else is refused), and only a line Stagewatch's parser takes is proposed. The desk keeps 400 characters of a line, so a message asked for the speaker's screen is at most 377 characters (Send now takes 500). `POST /api/proposals` (target `{"t":"main"}`, risk `review`); its state is read every 3 s and shown on the message, with its outcome as Stagewatch's `GET /api/proposals/<id>` states it at the top level: `ok` (true done, false failed or undelivered, null until it ran) and `words` (the target's or the desk's receipt words; `result` is the same string), kept on the message as `proposal.ok` and `proposal.words` — a settled state whose `ok` is not that boolean, or a state AGMessage does not know, is `unknown` (shown with ⚠, not final, asked again until it reads or the desk no longer has it) — `lost` when the desk no longer has it (it restarted — its frames' `seq` went back, or it handed the number out again — or the hall moved to another Stagewatch), never another proposal's of the same number (the line, the proposer and its time are compared). The line proposed is the line the desk keeps: no control characters (it drops them). Every line is held to a port of Stagewatch's tokenizer and parser (0.4's `… <urgency> ack` was refused: Stagewatch reads the third word as the flash). AGMessage takes one verb from any desk, only from what its collect lists as `approved` for this AGMessage's id: `notice <text>` (a notice in every open meeting, risk `review`), collected, run once — a restarted desk's new `p1` is a new proposal — and reported until the desk takes it (it lists a collected proposal only once, and turns one with no result in 5 minutes "undelivered", still taking a late one): its first post in the tick that collected it; then by the answer (`lib/deskresults.js`) — 2xx taken; 409, 404 and any other 4xx final; 429, or 503 with `Retry-After`, waits that long (1-120 s, 60 s unsaid) and leaves the whole link alone till then (Stagewatch's budget is per key, every route spends it — the desk and context loops both wait); 401 and 403 wait a minute (`AGM_DESK_AUTH_WAIT_MS`; a 401 also refuses the link's key, above); no answer or a 5xx backs off 3 s doubling to 60 s. Every post after the first reads the proposal back (`GET /api/proposals/<id>`) and posts only while its line, target and time are the ones that ran and it is `approved` or `undelivered` (`done`/`failed`: taken already; anything else, or a 404: gone) — so a restarted Stagewatch's proposal of the same number, seen or not, never gets this result. Waiting results (at most 200, the oldest pushed out and said) are kept in `desk-results.json` (mode 0600, the line and the words, never a key), saved before the first post and read back at start by type (a record for another node or without the proposal's time is dropped); the link they go through is the hall's Stagewatch, or the default the hall fell back on, while it is the same address — else they end "nobody to tell". The desk loop runs only once this copy holds its data folder; a link Stagewatch asked to wait, or whose key it no longer takes, gets nothing more that tick. Whether Stagewatch keeps a desk (its hello's `approvals`, else `GET /api/proposals?from=` once a minute) changes only on a verdict — 200 a desk, 404 or 405 none — and an answer that says nothing (no answer, 429, 5xx, 401) keeps it and asks again in 5 s, after any `Retry-After`, so a busy key never hides the desk for a minute (what it approved meanwhile would expire uncollected). Health `desk {waiting, oldestAt, lastStatus, nextAt}` and the admin page's health line count them; a result ended untaken, or taken after retries, is a recent event (no notice text, no ids). |
| Patterns and PlayMap | Linked by the admin (Admin → Show network → Link…) with the node's own pairing token, sealed in `settings.json` → `peerLinks`, optionally for one hall, and the first 16 or more characters (64 bits) of its certificate's fingerprint as the node shows it on its own screen (`fpTyped`; public, kept unsealed as hex). A node heard from one of this machine's own addresses is linked by 127.0.0.1. **The token is full control of the node, so it goes only to this machine or over a confirmed TLS connection**: to a loopback address (127.0.0.0/8, `::1`, `localhost`) in plain HTTP, or over TLS to the certificate pinned for that node by such a link (its own key, `peer:<id>`, apart from the Stagewatch link's first-use pins) or one a person confirmed by typing the start of its fingerprint (at link time, or Admin → Show network → Confirm certificate…; audited). A node on another machine that offers no TLS, or whose certificate nobody confirmed, is refused — red, with the reason — and sent nothing (a certificate read is a TLS handshake: nothing of AGMessage's goes with it). `GET /api/context` every 5 s with `X-Patterns-Token` / `X-PlayMap-Token` (never in a URL; pinned TLS when the node announces a certificate, the address is `https://` or the node is pinned — a pinned node is never polled in plain HTTP): its light, headline, attention items and verbs on the halls board and in the AI's brief of its own hall (a node linked for every hall: of every hall; never another hall's, neither as linked nor as heard on the network). A changed certificate is refused (red, CERTIFICATE CHANGED) until the admin types the start of the new one's fingerprint (Accept new certificate…; audited); a page is told that a certificate waits, never its fingerprint, nor a heard node's announced one, and no refusal's words name one, so the characters typed come from the node's own screen. Unlinking forgets the token and the pin. Driving it (`nodes.control`): a node linked for one hall by those with `nodes.control` in that hall; one linked for every hall only by those with it in every hall (and the admin), on the board too: a hall's row shows its nodes' lights to everyone who sees the hall, and the board offers Show network only to an account that may drive a node. **Never driven directly**: AGMessage holds only the operator's pairing token, so `nodes:command` with `mode: "send"` is refused with words (`PeerLink.send`), and nothing is posted to the node's `/api/cmd`; driving it directly waits for a key the node issues to AGMessage alone (Patterns' `ptk_`, PlayMap's `pmk_`). A line is only a verb its context lists (the longest match), rated as the node rates the line: its listed risk, raised (never lowered) by the words the node says raise it (`riskWhen`, `highFor` — from its context, or PlayMap's `GET /api/verbs`, read once per connection and asked again while it does not answer — until it has, a line to that PlayMap is proposed as high), and a line that carries a line (`BIND ADD … TO <line>`, `BIND LEARN <line>`) at least the riskiest reading of what it carries (the words after each `TO`) — high when it is JSON, quoted, unlisted or nested too deep. It is proposed with that risk to the show desk of the node's hall (its own Stagewatch, else the default; the default for a node of every hall) — refused when that Stagewatch keeps none, never sent to another hall's (target `{"t":"patterns"\|"playmap","id"}`), where a person approves it and the node collects it with its own key. Every link, certificate and proposal is audited; never the token, and never a verb's secret words: a line carrying one (`LINK PATTERNS <host> <token>`, or a binding or a JSON argument that carries it) is refused before it is proposed or recorded — the desk would keep it — and is set on the node itself; the refusal shows the line up to them. PlayMap's `ASSISTANT SET enabled\|provider`, which it rates high but publishes nowhere yet, is rated high here too. |
| Its context | `GET /api/context` (admin, or `Authorization: Bearer agn_…` — the read-only token on the admin page). Show Bus §6: meetings and people by role, open action-prompt questions, the count of open help requests, each Stagewatch link and its clock (a hall's by the Stagewatch's own name), AI and tunnel state, role-level recent events, one-hop peers (a linked Patterns or PlayMap with its own light and headline). **Never** message text, names, room names or codes, or documents; at most 32 one-hop peers, live ones first. Each linked Stagewatch is posted (`POST /api/peers/context`, on change and every 5 s) the context of the halls that follow it — their meetings, prompts and help count, their role-level recent events (with the node's own: a certificate renewed, a desk's notice), and its own link (another hall's events, and the light and headline of a Patterns or PlayMap linked for another hall, are left out: such a node heard on the network is named only as heard); `GET /api/context` is the whole node. |
| Stagewatch's context | `GET <sw>/api/context` on connect and every 5 s, per link: the admin page, the AI's brief, and the departments offered as destinations. |
| Health | `GET /api/health`: `{ok,version,build,uptime}` for anyone; restarts, last crash, watchdog give-up, event-loop delay (p50/p95/max), send-to-stage round trip, clock offset and save errors for the admin or the host laptop. |

## Without the internet

Everything above works on the local network alone. Only the AI drafts (Anthropic) and the Cloudflare tunnel need the
internet; when the AI can't be reached it says so and nothing else changes.
